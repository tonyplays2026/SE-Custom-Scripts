[h1]Track Cart Controller[/h1]
A Programmable Block script that holds a steady speed for a track-guided wheeled cart travelling between fixed points (e.g. a base and a mine), and can drive itself to a captured stop and dock automatically. It drives up grades, brakes down grades, and keeps speed under control through curves. Steering is assumed to be handled by the physical track — this script only manages propulsion, wheel brakes, and connectors.

[h2]How it works[/h2]
[list]
[*]Reads the cart's velocity from a Remote Control (or cockpit) and holds a configurable target speed.
[*]Proportional control: drives when below target, engine-brakes when slightly over, and engages the wheel brakes once overspeed passes a threshold.
[*]A sign-independent emergency brake triggers if total speed ever exceeds MaxSpeed — so a misconfiguration fails safe instead of running away.
[*]Only the drive wheels you designate are controlled; alignment/guide wheels are left untouched. Left/right sides are detected automatically and driven with opposite signs (Space Engineers applies wheel overrides raw, so mirrored wheels need opposite values).
[*]Stops are captured positions along the track. Driving to a stop uses a distance-based deceleration profile: cruise, then slow smoothly, crawl, and lock the connector.
[/list]

[h2]Setup[/h2]
[olist]
[*]Place a Programmable Block on the cart with a Remote Control (or any cockpit/control seat).
[*]Create a block group containing ONLY the drive wheels (not alignment/guide wheels). Default group name is [b]Drive Wheels[/b].
[*]Give each connector a distinct name (e.g. "Front Connector", "Rear Connector") so stops can remember which one docks where.
[*]Load the script, recompile. If Custom Data is empty it writes the config template.
[*]Capture your stops (see below).
[/olist]

[h2]Capturing stops[/h2]
Drive the cart to a stop and dock it manually so a connector is locked. Then run the PB with:
[code]setstop <name>[/code]
The script records that stop's position and the connector currently connected. Example: docked at the base with the front connector locked, run [b]setstop Base[/b]. Repeat at the other end, e.g. [b]setstop Mine[/b]. A cart with a connector at each end never needs to turn around — each stop remembers its own connector.

[h2]Commands[/h2]
Run the PB with one of these arguments (button, sensor, timer, event controller, or manually):
[list]
[*][b]next[/b] — drive to the OTHER stop automatically (two-stop shuttle). Fired while docked, it departs to the far end; if run while undocked it heads to the nearest stop to re-dock.
[*][b]goto <name>[/b] — drive to a specific stop, decelerate, and dock. Direction is chosen automatically.
[*][b]start[/b] — plain cruise along the track at CruiseSpeed (open-track testing; uses Reverse for direction).
[*][b]stop[/b] — halt and hold with brakes.
[*][b]setstop <name>[/b] — capture the current dock as a stop (see above).
[*][b]liststops[/b] — list captured stops.
[*][b]reload[/b] — re-read Custom Data and re-discover blocks.
[*](no argument) — print status / setup info to the PB detail panel.
[/list]

[h2]Automatic back-and-forth[/h2]
With exactly two stops captured, [b]next[/b] is the one-button shuttle trigger: the cart checks which connector is locked, and drives to the other stop. Wire [b]next[/b] to a button, timer, sensor, or event controller to run the route.

While the cart is docked it shares the base's terminal system, so a timer or event controller [i]on the base[/i] can run the cart's Programmable Block with the [b]next[/b] argument directly — no antenna or inter-grid messaging needed. This lets a separate loading/unloading routine dispatch the cart when it's ready.

[h2]Configuration[/h2]
Settings live in the PB's Custom Data, section [b][CartController][/b]:
[list]
[*][b]CruiseSpeed[/b] — target travel speed (m/s).
[*][b]MaxSpeed[/b] — emergency-brake threshold on total speed (m/s); must be greater than CruiseSpeed.
[*][b]Kp[/b] — proportional gain: propulsion override per m/s of error. Higher is more aggressive.
[*][b]BrakeOverspeed[/b] — m/s above target before the wheel brakes engage.
[*][b]PropulsionSign[/b] — global wiring flip (1 or -1). See troubleshooting.
[*][b]Reverse[/b] — plain-cruise travel direction (true/false); not used by goto.
[*][b]DriveWheelGroup[/b] — block group holding only the drive wheels.
[*][b]CrawlSpeed[/b] — minimum approach speed near a stop (m/s).
[*][b]ApproachDecel[/b] — deceleration used to plan the approach slowdown (m/s^2); lower slows earlier.
[*][b]ConnectDistance[/b] — distance to the stop at which to crawl and connect (m).
[/list]
Captured stops are stored in a [b][Stops][/b] section (auto-filled by setstop; also hand-editable).

[h2]Tuning[/h2]
[list]
[*]Start with a low CruiseSpeed and raise it once behaviour looks good.
[*]If the cart oscillates around the target speed, lower Kp; if it's sluggish, raise Kp.
[*]If it overshoots a stop, lower ApproachDecel (starts slowing sooner) or CruiseSpeed.
[*]If it stops short and won't connect, raise ConnectDistance slightly or check connector alignment.
[/list]

[h2]Troubleshooting[/h2]
[b]It emergency-brakes immediately or oscillates hard on start[/b]
Wheel propulsion is wired opposite to what the script assumes. Set [b]PropulsionSign = -1[/b], then reload.

[b]Plain cruise drives toward the wrong end[/b]
Set [b]Reverse = true[/b], then reload. (This does not affect goto.)

[b]"goto" says the connector was not found[/b]
The stop remembers a connector by name. If you renamed or rebuilt it, re-dock and run setstop again, or fix the name in the [Stops] section.

[b]The left/right wheel count looks wrong (not an even split)[/b]
The status panel shows a "left N / right N" breakdown. Sides are classified using the Remote Control's Right axis — if the controller is mounted rotated relative to travel, the split can come out lopsided. Re-check the drive-wheel group and that the controller faces along the track.
